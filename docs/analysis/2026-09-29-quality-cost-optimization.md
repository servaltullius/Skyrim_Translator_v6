## 로컬 LOTD의 실제 구성

대상은 로컬 **LOTD v6.7.2 XML**이다. 최신 버전 파일의 통계로 일반화하지 않는다. XML을 파싱한 뒤의 Unicode 글자 수이며 태그를 포함한다. 과금 토큰 수가 아니다.

| 항목 | 행 수 | 원문 글자 수 | 전체 글자 비중 |
|---|---:|---:|---:|
| 책 본문 `BOOK:DESC` | 1,410 | 4,214,150 | 83.42% |
| 응답 대사 `INFO:NAM1` | 5,134 | 397,434 | 7.87% |
| 나머지 전체 | 10,829 | 440,243 | 8.71% |
| 합계 | 17,373 | 5,051,827 | 100% |

`INFO:NAM1` 이외 INFO/DIAL도 일부 있으므로 두 번째 행을 모든 대사로 해석하면 안 된다. 책 제목 `BOOK:FULL`은 나머지에 포함되며 **1,419행·32,369자, 전체의 0.64%**다. 책 본문 중 8,000자 초과는 135개, 15,000자 초과는 28개, 최대는 39,639자다. 마스킹 후 크기와 실제 분할 횟수는 별도다.

중복도 행 수와 글자 수를 구분해야 한다.

| 중복 기준 | 제거 가능한 추가 행 | 추가 글자 | 전체 글자 대비 |

두 번째 기준도 대화 문맥·용어 치환까지 포함하는 실제 앱 중복 판정과 같지 않다. 첫 번째 수치는 문맥을 무시한 낙관적인 상한이다. **“중복 행 16.7% 제거 → 비용 16.7% 절감”은 이 데이터에서 성립하지 않는다.** TM은 같은 파일 내 중복 제거와 별개이며, 이전 버전의 검수된 장문을 재사용할 때 더 큰 효과가 가능하다.

## 품질 개선에서 먼저 다룰 문제

### 책 제목과 본문을 분리한 정책

`MainViewModel.Translation.cs`의 `IsBookFullRec`는 BOOK이면서 하위 필드가 FULL로 시작하는 경우만 선택한다. `TranslationRunnerService.CollectBookFullIds`가 이 결과로 모델을 분기한다. 따라서 **기본 모델 Lite + BOOK:FULL 모델 3.8 설정은 책 본문을 Lite로 번역한다.** 현재 기본값은 전체 3.8이고 이 옵션은 꺼져 있으므로, 기본 설정에서 이미 잘못 분기하고 있다는 뜻은 아니다.

제안: 제목·본문·대사·퀘스트·UI를 명시적으로 구분하고, 미리보기에서 각 모델이 맡는 행 수와 원문량을 보여준다. 특히 기존 BOOK:FULL 옵션의 의미를 바꿀 경우 저장된 설정을 조용히 재해석하지 말고 이전 규칙을 보존하거나 새 정책으로 명시적으로 이전해야 한다.

장문은 `TranslationService.LongText.Chunks.cs`에서 페이지 경계 우선 분할과 실패 시 재분할을 이미 수행한다. 청크 간 공백 보존도 수정되어 있다. 다음 개선은 이를 다시 만드는 것이 아니라 **책 제목·확정 용어·서술 시점·앞뒤 원문의 짧은 참조 문맥**을 청크에 일관되게 전달하는 것이다. 앞 청크 번역을 무제한 누적하면 입력 비용과 오역 전파가 늘므로, 참조 전용 문맥에 상한을 두고 출력 대상과 구별해야 한다.

문단 단위 문맥이 문장별 번역보다 유리했던 연구가 있지만 중요한 오류도 남았다. 이를 Skyrim 한국어/현재 모델의 개선률로 환산할 수는 없다. [Karpinska & Iyyer, WMT 2023](https://aclanthology.org/2023.wmt-1.41/).

### 자동 용어의 강제 적용과 TM 신뢰도

`TranslationService.SessionTermMemory.AutoGlossary.cs`는 학습된 항목을 `Auto(Session)`, `Enabled=true`, `Substring`, `ForceToken`으로 프로젝트 용어집에 저장한다. `SessionTermMemory.Memory.cs`는 일관성을 위해 첫 매핑을 유지한다. 기존 용어를 덮어쓰지 않는 보호와 후보 필터는 있지만, **처음 생성한 자연스러운 오역이 후속 문장에 강제될 위험**은 남는다. `IsSessionTermRec`에 `:NAM`도 포함되어 있어 짧은 대사 조각이 이름 후보로 들어갈 여지도 점검할 가치가 있다. 실제 오염 빈도를 측정했다는 뜻은 아니다.

제안: 검수한 용어와 자동 제안을 구분하고, 자동 용어는 기본적으로 참고 힌트로 쓰되 확정된 고유명사만 강제 치환한다. REC·문맥·원래 대소문자·첫 생성 모델·검수 상태를 함께 보존하고, 수정한 용어가 사용된 행을 추적한다. Reach 같은 예외를 계속 늘리는 것보다 출처와 의미 범위를 관리하는 쪽을 우선한다.

TM은 이미 프랜차이즈별이며 프로젝트 TM이 프랜차이즈 TM보다 우선한다. 하지만 저장 키는 원문 중심이다. 현재 선택 집합 안에서 문맥 충돌을 발견하면 재사용을 피하므로, **다른 작업이나 다른 선택 집합에서 생긴 충돌까지 해결한 상태는 아니다.** 검수 등급·REC/EDID·용어집 버전을 포함한 확장 키와, 기존 source-only TM을 후보로 취급하는 이전 전략을 검토한다. 유사 원문 TM은 숫자·부정·퀘스트 조건이 바뀔 수 있으므로 자동 확정 대신 검수/번역 참고로 사용한다.

로컬 `tm/`에는 Fallout/Starfield 자산이 있다. TES에 섞으면 안 된다. `Skyrim_Latest_Kor`의 한글 문자열만으로 영어→한국어 매핑을 확정할 수 없으므로, 일치하는 버전의 영어 STRINGS와 ID 대응 또는 검수된 양언어 XML을 확보한 뒤 적중률을 계산해야 한다. 이번 조사에서는 사용자 DB를 열어 실제 TM 적중률을 측정하지 않았다.

### 의미 검증과 문맥 정확도

`TryGetQualityEscalationTrigger`는 미번역, 조사 표기, 중복/오타 패턴, 퍼센트 오류를 감지한다. **유창한 오역, 부정 반전, 누락된 조건, 화자 관계, 추가한 설정을 일반적으로 판별하는 의미 평가기는 아니다.** 기본값도 품질 승격 꺼짐이다. Lite 결과가 자동 검증을 통과했다고 3.8과 동등한 의미 품질이라고 볼 수 없다.

형식 검사와 의미 검수를 분리한다. 수량·부정·주체/대상·퀘스트 조건·고유명사·내용 누락을 우선 검토하고, 언어별 단순 단어 비교는 경고 수준으로 제한한다. 고위험 항목만 추가 모델 평가나 사람 검수에 보내되, 같은 모델의 자기평가를 정답으로 쓰지 않는다. 전수 재작성은 기본 정책으로 권하지 않는다. 2026년 문학 번역 연구에서도 재작성의 이득이 주로 유창성에 집중되고 의미 충실도 개선은 제한적이었다. [Tan et al., ACL 2026](https://aclanthology.org/2026.acl-long.268/).

대화 문맥은 `BuildDialogueContextWindowForIndex`에서 EDID 접두부와 주변 행을 사용하며 EDID가 없으면 인접 행으로 대체한다. 이는 실제 대화 연결을 보증하지 않는다. 로컬 LOTD의 INFO/DIAL 6,041행에는 모두 EDID가 있어 빈 EDID 대체 경로는 이 파일에서 발생하지 않지만, 다른 파일에서는 별도 검증이 필요하다. 확인 가능한 동일 레코드·연결 정보만 사용하고, 불확실한 항목은 “주변 참고 문자열”로 표시하며 화자/관계를 추정하지 않는 정책을 권한다.

## 비용 개선에서 먼저 다룰 문제

### 사용량 계측과 실패 비용

성공 응답의 `CompletionTokens`는 추론을 포함하도록 이미 수정됐다. 남은 문제는 `GeminiClient.GenerateContent.cs`가 `MAX_TOKENS`·불완전 응답·최종 텍스트 없음 예외를 **usage 반환 전에** 던진다는 점이다. 외부 catch는 사용량 없는 실패 로그를 남긴다. 서버가 usage를 보내 준 실패 응답도 잃을 수 있으므로, 실패한 설정의 비용을 과소평가할 수 있다. 정확히는 0달러가 아니라 미상이다.

제안: 응답 수신 시 HTTP 상태·finish reason·원본 usage를 먼저 보존하고, 번역 결과의 채택 여부를 별도로 기록한다. 로그에 run/request/row/chunk ID, 모델·추론 수준·서비스 등급, 번역/수리/재시도/승격 목적, 입력·출력·추론·캐시 토큰을 추가한다. 캐시 생성 응답의 토큰·보관 시간도 보존한다. 생성 비용 추정과 서비스 청구 확정액을 구별하고, 미상 호출 수를 함께 보여준다.

### 불필요한 캐시·반복 요청 감소

현재 캐시는 `TranslateIdsCoreAsync` 시작 시 TM 선별 전에 생성한다. 2시간 TTL이며 실패 시 해당 실행에서 비활성화한다. 모든 행이 TM으로 해결되거나 남은 행이 거의 없어도 캐시 생성을 시도한다. 캐시 객체에는 시스템 프롬프트만 들어가고, 각 요청의 형식 규칙·조건별 힌트 등은 별도로 전송된다.

제안: 재사용·중복 선별 이후 실제 생성 요청이 있을 때 지연 생성한다. 적은 요청에는 캐시를 생략하고, 성공/미지원/최소 길이 미달을 구별한다. 안정적인 공통 지시를 앞에 두되 글자 수만으로 토큰 조건 충족을 단정하지 않는다. 공식 문서의 3.8 implicit cache 최소 입력은 4,096토큰이며, explicit도 모델별 최소치 확인이 필요하다. 캐시 조건을 맞추려고 불필요한 문장을 채워 넣지 않는다. [generateContent 캐시 문서](https://ai.google.dev/gemini-api/docs/generate-content/caching).

공통 입력 S토큰을 N회 사용할 때 비교식은 `캐시 절감 = N×S×(일반 입력 단가−캐시 읽기 단가)/1M − 보관 비용 − 기타 추가 비용`이다. 실제 캐시 적중 토큰과 TTL을 대입해야 한다. 전체 비용 대부분이 출력이라면 입력 캐시만으로 큰 전체 절감률을 얻기 어렵다.

실패 시 재시도·반분·장문 재분할·수리가 겹칠 수 있다. 요청별 `MaxRetries=3`은 행/작업 전체의 총 요청 예산이 아니다. 오류 원인에 맞게 크기를 조절하고, ID 대응과 무결성이 확인된 부분만 안전하게 재사용하며, 작업별 비용·재시도 상한을 둔다. 이미 행별 수리 경로가 있으므로 전부 새로 구현하기보다 실제 로그에서 낭비가 큰 경로를 먼저 찾는다.

| 3.8 Flash Flex/Batch | $0.375 | $1.875 | 미구현 |

3.8 가격은 2026-12-31까지이며 2027-01-01부터 위 3.8 입력·출력 단가는 두 배가 된다. 현재 가격표 코드에는 날짜 분기가 있다. [Google 공식 가격표](https://ai.google.dev/gemini-api/docs/pricing).

**Flex:** generateContent에서도 지원하는 동기식 할인 경로다. 앱에는 서비스 등급 필드가 없어 아직 사용하지 않는다. 기존 15분 HTTP timeout은 출발점이 되지만, 429/503·긴 대기·사용자 중단·가격 기록·Standard 전환 정책을 별도로 설계해야 한다. 미리보기 기능이며 지연/가용성이 가변적이다. 기본 모델을 바꾸지 않고 시험할 수 있어 Batch보다 작은 첫 실험 후보로 판단한다. 서버는 혼잡 시 자동으로 Standard로 올려 주지 않는다. [공식 Flex 문서](https://ai.google.dev/gemini-api/docs/generate-content/flex-inference).

**Batch:** 현재 UI의 BatchSize는 여러 행을 한 일반 요청에 담는 설정이다. 공식 Batch API 할인과 다르다. 공식 Batch는 비동기이며 목표 처리 시간은 24시간이다. 작업 ID·입력 해시·행 매핑을 디스크에 저장하고 앱 재시작 후 조회/재개, 부분 실패 수리, 중복 제출 방지가 필요하다. 생성 요청 자체가 멱등하지 않으므로 통신 오류 때 무조건 재제출하면 안 된다. [공식 Batch 문서](https://ai.google.dev/gemini-api/docs/batch-api).

Batch에서는 실행 중 바뀌는 세션 용어를 제출된 요청에 소급 반영할 수 없다. 확정 용어를 먼저 고정한 뒤 본문 요청을 제출하는 단계가 필요하다. 대기 중 캐시 만료와 보관 비용도 고려한다. Batch 문서는 캐시 표준 요금을 언급하고 가격표는 Batch 캐시 요금을 별도로 제시하므로, 도입 전 적용 요금을 재확인한다. 이번 계산은 캐시를 결합하지 않는다.

### 수치로 보는 선택의 차이

아래는 **실측 비용이 아닌 동일 토큰 가정의 계산**이다. 입력 300만 + 출력/추론 300만, 캐시·수리·세금 제외:

| 가정 | 생성 비용 | 3.8 Standard 대비 |
|---|---:|---:|
| 3.8 Standard | $13.50 | 기준 |
| 같은 토큰의 3.8 Flex 또는 Batch | $6.75 | 50% 감소 |
| 같은 토큰의 3.1 Lite | $5.25 | 61.1% 감소, 품질 동등 가정 불가 |
| Lite 후 토큰량 20%를 3.8로 다시 번역 | $7.95 | 41.1% 감소, 탐지 누락·추가 문맥 비용 제외 |

마지막 행의 재번역 비율은 **행 비율이 아닌 비용을 유발하는 토큰량 비율**이다. 여기서는 `5.25 + 13.50×재번역비율`이며 약 61.1% 이상을 다시 번역하면 Standard 3.8 직행보다 비싸진다. 다른 토큰량·추론·검수 방식에서는 경계가 달라진다.

책을 전부 3.8에 두고 나머지만 Lite로 바꾸면, 본문/나머지의 비용이 원문 글자 수에 비례한다는 단순 가정하에 전체 절감은 약 **10~11%**다. 짧은 문장에서는 공통 지시 오버헤드가 더 크므로 실제 비율은 달라질 수 있다. 할인·TM·캐시·라우팅 절감률을 단순 합산하면 안 된다.

추가 절감으로 세면 안 되는 항목도 있다. 3.8 Low/3.1 Minimal은 이미 적용했다. Gemini 3.x에서는 코드가 다중 후보를 1개로 제한하므로 현재 “후보 재순위 끄기”만으로 후보 3개 분량의 비용이 줄지는 않는다. 세션 초기 용어 20개는 실제 번역 대상에서 골라 처리하고 완료 항목을 본 큐에서 제외하므로, 모두 불필요한 이중 번역이라고 계산해서도 안 된다.

## 검증 설계

기존 [LOTD 비교](../../benchmarks/translation/lotd-v1/README.md)는 raw 웹 응답이다. 3.8은 확보한 116행 중 형식 통과 114행, Lite는 확보한 119행 중 112행이다. 두 모델 모두 120행 전체 응답을 확보한 것은 아니며, 일부 파일은 동일한 예비 요청을 재사용했다. usage는 없고 120행 전체의 의미 검수도 수행하지 않았다. 이 결과를 앱의 최종 성공률·유료 비용·독립 반복 표본으로 사용하면 안 된다. 앱의 JSON 배치와 장문 텍스트/sentinel 경로도 다르다. JSON schema는 값의 의미까지 보장하지 않는다. [공식 structured output 문서](https://ai.google.dev/gemini-api/docs/generate-content/structured-output).

1. **오프라인 기반 검증:** 잘린 응답도 usage를 보존하는 fixture, TM 100% 적중 시 캐시 미생성, BOOK:FULL/DESC 분기, 자동 용어의 검수 상태, 취소/재개와 요청 예산을 확인한다. 안전한 XML 왕복과 기존 회귀 테스트는 계속 유지한다.
2. **앱 기준선:** 고정된 120개에 실제 파이프라인을 적용한다. 별도 긴 책 표본은 15,000자 이상/다중 페이지를 포함한다. 프롬프트·용어집·TM·모델·설정 해시를 저장하고, 3.8 Low 기준으로 새 응답을 확보한다. 유료 실행은 별도 실행 단계에서 예산을 정해 수행한다.
3. **한 번에 한 요소 비교:** 문맥/용어 정책, 캐시, Flex, 선택적 Lite를 각각 기준선과 비교한다. 책 품질을 먼저 확인한 뒤 Batch와 결합한다. 작은 탐색 표본에서 후보를 줄이고 별도 검증 표본으로 다시 확인한다.
4. **판정:** 형식 무결성, 중대 의미 오류, 용어 일관성, 누락/첨가, 자연스러움, 사람 수정 시간을 분리한다. 모델명과 실행 순서를 가린 검수를 권한다. 가능한 경우 두 검수자가 독립 평가하고 불일치는 근거를 남긴다. 문서 문맥과 전문 오류 분류를 사용하는 MQM 연구를 평가 설계의 근거로 삼되, 이번 프로젝트에 맞춘 축약 기준임을 명시한다. [Freitag et al., TACL 2021](https://aclanthology.org/2021.tacl-1.87/).

| 지표 | 계산/기록 | 채택 기준 제안 |
|---|---|---|
| 최종 무결성 | ID·태그·변수·이미지 경로·개행·페이지 구조 | 테스트/평가 표본에서 손상 0건; 실패 행을 완료로 저장하지 않음 |
| 의미 품질 | 부정·조건·수량·주체 오류, 누락/첨가를 심각도로 구분 | 새 중대 오류 0건을 초기 기준으로 삼고 표본 한계를 함께 보고 |
| 재사용 품질 | 검수된 TM/용어 적중량 및 잘못 적용한 사례 | 적중 행 수와 원문량을 모두 보고, 오적용을 별도로 집계 |
| 총 생성 비용 | 채택/폐기/수리/재시도 포함 usage 기반 비용 + 캐시 보관 | 미상 사용량을 0으로 계산하지 않음 |
| 비용 효율 | 총 비용 ÷ 검수 통과 원문 1,000자 | 품질 기준을 만족한 설정끼리 비교 |
| 사용자 작업량 | 수정 시간/1,000자, 실패 복구 횟수, 전체 소요 시간 | API 절감과 수동 수정 증가를 함께 비교 |

465개 회귀 테스트 통과는 프로그램 동작의 근거다. 위 의미 품질과 실제 비용의 개선을 입증하는 숫자는 아직 아니다. **다음 구현 묶음은 계측 보완 + 책 본문 분기 + 자동 용어 신뢰도 + 캐시 지연 생성으로 제한하고, 그 결과를 측정한 뒤 Flex와 선택적 Lite를 평가하는 것을 권한다.**
