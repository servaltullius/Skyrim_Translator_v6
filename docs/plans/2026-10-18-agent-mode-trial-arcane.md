## 헷갈렸거나 고쳐야 할 점

### CLI

1. **submit이 저장하지 않은 줄과 이유를 말해야 한다.** 예: "저장한 줄: 28, 다시 물을 줄: 1 (id 93: `<mag>` 위치가 수치 문맥이 아님)". 지금은 모델도 사용자도 왜 같은 줄을 다시 받는지 모른다. 그래서 같은 답을 되풀이해 요청을 낭비하기 쉽다.
2. **고쳐 쓰기 요청에도 이유를 넣어야 한다.** request.md의 CURRENT 옆에 검사가 짚은 문제(예: "`<mag>`는 수량 명사 앞에: `<mag>의 피해`, `<mag>포인트`")를 한 줄 넣는다.
3. **재export가 처리 안 된 예외로 죽는다.** 같은 키로 다시 export하는 것은 edit 뒤에 늘 하는 일이다. `output\<키>-2`처럼 새 폴더를 자동으로 고르거나, 스택 트레이스 없이 "이미 있는 폴더입니다. `export <키> <새 폴더>`로 다른 곳에 저장하세요"라고 안내해야 한다. AGENTS.md 5단계도 이 경우를 다뤄야 한다.
4. **줄 목록을 볼 명령이 없다.** `edit`는 `order`를 받는데, check에 안 나온 줄의 순번을 알 길이 없어 SQLite를 직접 읽었다(읽기 전용). `tullius show <키> [--find 텍스트] [--rec WEAP:FULL]`처럼 `#순번 / 원문 / 번역`을 출력하는 명령이 필요하다. 끝까지 읽고 용어를 맞추는 검토(Blast/Explosion 같은 경우)에 꼭 있어야 한다.
5. **request의 id와 check·edit의 순번이 하나 차이 난다.** request·check 메시지의 id는 DB Id, `#숫자`와 edit의 order는 OrderIndex라 id = order + 1이다. check 한 줄에 "#224 … id=225"처럼 두 번호가 같이 나와 헷갈린다. 하나로 맞추거나 edit가 id도 받게 한다.
6. **edit가 무엇을 바꿨는지 되풀이해 보여 주지 않는다.** "고친 줄: 1"만 나온다. `#249 Staff of Arcane Blasts: 비전 폭발 지팡이 → 비전 작렬 지팡이`처럼 원문과 전후를 출력하면 순번 실수를 바로 알 수 있다.
7. **고쳐 쓰기를 거친 줄 끝에 공백 2칸이 붙는다.** 같은 원문 줄 두 개(#92·#94)가 모두 "…늦춥니다.  "로 저장되었다. 단건 요청의 문장 끝 표시(`__XT_PH_9999__`)를 걷어 내는 경로가 의심된다. 재현해서 확인해 봐야 한다.
8. **check의 Info 메시지가 내부 진단 영어다.** "tm_fallback: … Protected text mismatch for id=225 tm post-edits: (expected 3, got 4)"는 모델도 사용자도 손댈 수 없다. 기본 출력에서 숨기거나 "게임 번역 대신 직접 번역을 썼습니다(고칠 것 없음)"처럼 한국어로 바꾼다. 메시지 중간에 줄바꿈이 들어가 한 건이 두 줄로 갈라지는 문제도 있다.
9. **submit 뒤 answer.txt가 그대로 남는다.** 앞 요청의 답을 다음 요청에 잘못 내는 실수가 쉽다(2번 실패의 원인). 답의 id가 지금 요청과 하나도 안 맞으면 "이전 요청의 답 같습니다"라고 짚어 주거나, 저장에 성공하면 answer.txt를 `responses\`로 옮긴다.

### request.md

10. **고쳐 쓰기 요청의 '답하는 법'이 틀렸다.** 단건 번역과 같은 머리말("`<<<TEXT`와 `TEXT>>>` 사이의 글을 옮기고, 끝의 `__XT_PH_9999__` 포함")이 나온다. 그런데 본문에는 `<<<SOURCE`/`<<<CURRENT`만 있고 `__XT_PH_9999__`는 없다. "CURRENT를 고친 번역문만 쓴다, 끝 표시는 없다"로 따로 써야 한다.
11. **고정 지시가 요청마다 되풀이된다(요청당 약 6~7천 자).** 이 양이 사용량의 절반 넘게 차지한다. GUI와 같은 프롬프트를 지키는 것이 목적이라도, 에이전트 모드에서는 `work\<키>\instructions.md`에 한 번 쓰고 request.md에는 지시가 바뀐 경우에만 다시 넣는 식으로 줄일 여지가 크다(해시로 판단). 큰 모드에서 500줄당 5시간 한도 약 5%를 쓰는 것을 생각하면 효과가 가장 큰 개선이다.
12. **요청을 넘어서는 용어 일관성.** 같은 단어(Arcane, Blast, Pull 등)가 요청 여러 개에 흩어져 나온다. 모델이 앞 요청에서 정한 번역을 기억하지 못하면 어긋난다. 이번에도 Blast/Explosion이 한 번 어긋났다. request.md에 "이 프로젝트에서 이미 저장한 비슷한 원문 → 번역" 몇 줄을 참고로 넣으면 좋다(GUI의 세션 용어 `__XT_TERM_SESS_`와 같은 역할).
13. **`<mag>` 어순 규칙을 미리 알려야 한다.** 지시에는 "숫자 토큰에 조사를 붙이지 말라"만 있다. 그런데 검사는 `<mag>`가 수량 명사 앞에 오기를 기대하는 것으로 보인다. 이 기대를 예시와 함께 적으면 1번의 재요청이 처음부터 안 생긴다.

## 잘 된 점

- open부터 export까지 명령 7종이 설명대로 동작했고, 사용자 GUI 프로젝트는 건드리지 않았다(`--projects`).
- 같은 원문 줄은 한 번만 물어보고 나머지에 복사해서 172개 답으로 279줄을 채웠다.
- JSON 형식 실패는 저장하지 않고 같은 요청을 남겨 둬서 다시 내기 쉬웠다.
- 용어 토큰(`__XT_TERM_G…`)과 힌트(`⟦XT_TERM=…⟧`)로 아트로나크·주문서·마법책 표기가 저절로 맞았다.

### 남은 것과 다음 후보

- **줄마다 되풀이되는 `style` 문자열.** 2차 request.md의 대부분이 이것이다. 묶음 30줄 중 DNAM 20줄이면 같은 330자 문자열이 20번(약 6.6천 자) 나온다. 표시만 바꿔 instructions.md의 절이나 요청 머리의 범례 하나로 모으면, 읽는 양이 다시 절반 가까이 줄 것으로 보인다(요청 해시는 그대로).
- **Core의 시간 문맥 오판.** `TokenSanitizer.IsTokenInTimeContext`가 수치 토큰 뒤의 '주고·줍니다'를 시간 단위 '주'로 읽는다. GUI의 API 번역에서도 같은 재요청과 비용이 생긴다. 에이전트 모드는 안내로 피하게 했을 뿐이고 검사는 그대로다. '주'·'일' 뒤에 한글 글자가 이어지면 시간 단위로 보지 않는 식으로 Core를 고치는 것을 따로 검토할 만하다(GUI 동작이 바뀌니 별도 작업).
  - **고침:** 한 글자 단위(초·분·일·주·년·간) 뒤에 한글이 이어지면, 그 글자가 조사·서술격·시간 말(간·동안·마다·후·째·의·입니다 등)일 때만 단위로 본다. '주는'·'주도록'은 주다로 본다. 지속시간 토큰의 '초 동안·초간·초마다·일째'는 그대로 통과한다.
- **고쳐 쓰기 경로의 끝 공백.** GUI에서도 모델 출력이 줄바꿈으로 끝나면 같은 증상이 난다(`TrySemanticRepairAsync` 결과는 다듬지 않는다). 에이전트 모드만 막았다.
  - **고침:** 고쳐 쓰기 결과도 첫 답처럼 원문의 앞뒤 공백에 맞춘다(`RestoreSourceEdgeWhitespace`).
