# 구독 앱으로 번역하기 (에이전트 모드) 설계안

2026-10-18 작성, 같은 날 코드와 대조해 검수(녹화·재생 범위, 중단 처리, 샌드박스, GUI 코드 위치). 아직 구현 전이다.

## 목표

API 키 없이 **구독만으로** 툴리우스 번역기를 쓰게 한다.

- 사용자는 이미 결제한 앱에서 번역기 폴더를 연다.
  - Claude 앱(Claude Code, Pro/Max)
  - ChatGPT의 Codex(Plus 이상)
  - 구글 안티그라비티
- 그리고 "이 모드 번역해 줘"라고 말한다.
- 그 앱의 모델이 번역기의 로컬 도구를 실행하며 번역한다. 결과는 지금 API 번역과 같은 형식, 같은 검사를 거친 플러그인이다.

### 지켜야 할 원칙

1. **번역기 도구는 AI를 부르지 않는다.** 네트워크도 API 키도 쓰지 않는다. 모델이 필요한 일은 모두 사용자가 대화하는 앱의 모델이 한다.
2. **번역기가 구독 앱을 몰래 실행하지 않는다.** EXE가 `claude -p`, `codex exec`, Gemini CLI를 뒤에서 부르면 구독을 다른 프로그램이 쓰는 셈이다.
   - Anthropic은 다른 개발자가 자기 제품에 claude.ai 로그인이나 사용량을 붙이는 것을 허용하지 않는다(Agent SDK 문서).
   - Gemini CLI 약관은 다른 프로그램이 그 로그인으로 서비스에 접근하는 것을 위반으로 본다.
   - 그래서 항상 사용자가 앱에서 대화로 시키는 흐름이어야 한다.
3. **정확해야 하는 일은 도구가, 문장은 모델이 한다.** 모델마다 성향이 달라도 태그 보호, 줄 수 검증, 저장 형식은 똑같이 지켜져야 한다.

## 전체 흐름

```
사용자 ──대화──▶ 구독 앱의 모델 ──명령 실행──▶ tullius(로컬 CLI) ──▶ 프로젝트 DB
                     ▲   │                         │
                     │   └── 요청 파일 읽기 ◀──────┘ (번역할 묶음, 프롬프트)
                     └────── 번역 결과 파일 쓰기 ──▶ submit (검증·후처리·저장)
```

1. `open`: 플러그인을 가져와 프로젝트를 만든다. GUI의 "플러그인 열기"와 같다.
2. `context`: 모드 요약·용어·말투(프로젝트 맥락)를 모델이 써서 저장한다.
3. `next` → 모델 번역 → `submit`을 반복한다. 사용량 한도에 걸리면 멈추고, 다음 대화에서 "이어서"로 계속한다.
4. `check`: 품질검사를 하고, 모델이 `edit`로 고친다.
5. `export`: 번역된 플러그인을 저장하고 결과를 보고한다.

프로젝트 DB는 GUI 번역기와 같은 파일(`%LOCALAPPDATA%\XTranslatorAi\Projects\...`)을 쓰는 것이 목표다. 그러면 에이전트로 번역한 프로젝트를 GUI에서 그대로 열어 검수할 수 있다. 앱 샌드박스 때문에 안 되면 키트 폴더 안에 둔다(아래 명령 절 참고).

## 핵심 설계: 기존 파이프라인을 "녹화·재생"으로 재사용

번역 파이프라인(`TranslationService`)은 다음을 이미 한다.

- 묶음 만들기(`TranslationBatching`)
- 태그·자리표시자 보호(`PlaceholderMasker`)
- 용어집 토큰(`GlossaryApplier`)
- 내장 TM·게임 사전·이전 번역 참조
- 대화 맥락과 화자
- 프롬프트(`TranslationPrompt`)
- 응답 해석(`TranslationResultParser`, JSON)
- 토큰 검증(`TokenValidator`)
- 후처리(`KoreanTranslationFixer`, `TranslationPostEdits`, `PromptLeakCleaner`)

이것을 다시 만들지 않고 모델 호출 지점(`IGeminiClient`)만 바꾼다. 실행 연결(게임 사전으로 끝나는 줄, 전역 TM, 저장된 번역 설정)은 GUI의 `TranslationRunnerService`가 하므로 CLI도 그것을 그대로 부른다. 게임 사전으로 끝나는 줄은 요청을 만들지 않으니 구독 사용량도 들지 않는다.

- **요청 범위: 남은 줄 전체**
  - 한 실행은 언제나 남은(대기·오류) 줄 전체로 시작한다. GUI가 "전체 번역"을 누를 때와 같다.
  - 대화 맥락 창(`BuildDialogueContextWindowMap`)과 TM 모호성 판단은 요청에 들어온 행 ID만으로 만들어진다. 그래서 한 묶음의 행만 넘기면 앞뒤 대사 맥락이 빠지고 GUI 번역보다 품질이 떨어진다.
  - 동시성은 1로 두어 묶음 순서를 항상 같게 한다.
- **녹화(`next`)**
  - `RecordingClient`로 실행을 시작한다. 첫 생성 호출이 오면 그 요청(프롬프트, 대상 행 ID, 프롬프트 해시, 모델 프로필)을 요청 파일로 저장한다.
  - 그다음 실행 취소 토큰으로 멈춘다. 일반 예외를 던지면 분할 재시도(`SplitFallback`)가 같은 줄을 반씩 다시 요청하므로 쓰면 안 된다. 취소(`OperationCanceledException`)는 파이프라인이 그대로 위로 던진다.
  - 멈춘 뒤에는 `ResetInProgressToPendingAsync`로 "번역 중" 표시를 되돌린다. GUI가 중지할 때와 같은 처리다.
- **재생(`submit`)**
  - 남은 줄 전체로 실행을 다시 시작한다. `ReplayClient`는 요청 파일의 프롬프트(해시가 같은 것)에는 사용자가 받은 결과를 돌려준다.
  - 파이프라인이 평소처럼 해석·검증·후처리해서 저장한다.
  - 처음 보는 생성 호출이 오면 다음 요청으로 녹화하고 멈춘다. 다음 묶음일 수도 있고, 검증 실패에 따른 재요청일 수도 있다. 그래서 `submit`의 결과에는 언제나 다음 요청 파일이 함께 나온다. `next`는 처음 시작할 때와 끊긴 뒤 다시 시작할 때만 쓴다.
  - 재생 때 첫 생성 호출의 프롬프트 해시가 요청 파일과 다르면 아무것도 저장하지 않고 거부한다. 녹화와 제출 사이에 DB가 바뀐 경우다.
- **결정성을 위해 끄거나 고정할 것**
  - 대기 중인 요청은 한 번에 하나만 둔다. 요청 파일이 있으면 `next`는 거부한다. 앞 묶음을 저장하면 TM·이름 기억이 바뀌어 뒤 묶음의 프롬프트도 바뀌기 때문이다.
  - 생성이 아닌 호출도 처리해야 한다. 묶음 크기를 정하는 토큰 세기(`CountTokensAsync`)에는 글자 수에서 계산한 고정 추정값으로 답하고, 녹화하지 않는다.
  - 프롬프트 캐시(`EnablePromptCache`, 기본 켜짐), 후보 재순위(`EnableRiskyCandidateRerank`, 기본 켜짐), 품질 상향, 세션 용어 기억은 끈다. 재시도는 1회로 줄인다.
  - 모델 이름에 따라 묶음 크기·출력 예산·정책이 달라진다(`GeminiTranslationPolicy`, `TranslationOutputBudget`). 그래서 에이전트 모드용 고정 모델 프로필을 하나 정하고, 요청 파일에 기록한다.
- **GUI와 달라지는 점**
  - 실행 안에서 쌓이는 이름 기억(`RunNameMemory`)은 `submit`마다 새로 시작한다. 묶음 사이에 이름 표기가 흔들릴 수 있으니, 시험판에서 품질검사의 이름 일관성 결과로 확인한다. 문제가 크면 기억을 작업 폴더에 남기는 방법을 검토한다.

장점: 품질 규칙이 GUI(API) 번역과 같고, 한쪽을 고치면 양쪽에 반영된다.

## 명령 (`tullius.exe`)

| 명령 | 하는 일 |
|---|---|
| `projects` | 프로젝트 목록과 진행률 |
| `open <플러그인 경로> [--data <게임 Data 폴더>]` | 프로젝트 만들기(GUI와 같은 가져오기). 이미 있으면 그대로 연다. 현지화 플러그인은 Strings·BSA가 필요하므로 GUI에 저장된 게임 경로를 쓰고, 없으면 `--data`로 받는다 |
| `status <프로젝트>` | 남은 줄 수, 대기 중인 요청 파일, 마지막 작업 |
| `context <프로젝트> --material` | 맥락 작성 재료 출력(레코드 종류, 자주 나오는 용어, 표본). 지금 `ProjectContextScanner`가 모으는 것 |
| `context <프로젝트> --set <파일>` | 모델이 쓴 맥락 저장(GUI와 같은 형식) |
| `next <프로젝트>` | 첫 요청(또는 끊긴 뒤 다시 시작할 요청) 파일을 만들고 경로·요약·글자 수·추정 토큰 출력. 대기 중인 요청이 있으면 거부 |
| `submit <프로젝트> <결과 파일>` | 재생해서 검증·후처리·저장. 받은 줄, 거부한 줄과 이유, 다음 요청 파일(없으면 끝) |
| `lookup <용어>` | 용어집·내장 TM·게임 사전에서 표기 찾기(모델이 이름을 지어내지 않게) |
| `check <프로젝트>` | 품질검사(GUI와 같은 `LqaScanner`, 화자별 말투 포함) 결과 |
| `edit <프로젝트> <파일>` | 줄 고치기(GUI 직접 수정과 같이 "수정됨"으로 저장) |
| `export <프로젝트> [출력 폴더]` | 번역된 플러그인·Strings 저장 |

- 모든 명령은 사람이 읽는 출력과 `--json` 출력을 함께 지원한다.
- 요청·결과 파일은 키트 폴더 안의 작업 폴더(`work\<프로젝트>\`)에 둔다. 에이전트 앱은 연 폴더 밖에 쓰는 것을 막거나 매번 허락을 묻는다(Codex 샌드박스, Claude Code 권한). 모델이 직접 쓰는 결과 파일은 반드시 연 폴더 안이어야 한다.
- 프로젝트 DB는 GUI와 같은 `%LOCALAPPDATA%\XTranslatorAi\Projects`가 목표다. 다만 도구 자신이 쓰는 것도 앱 샌드박스에 막힐 수 있으니 시험판에서 앱별로 확인한다. 막히면 키트 폴더 안의 `projects\`를 쓰고, GUI에서 그 프로젝트를 여는 방법을 따로 마련한다.
- DB는 언제나 도구만 쓴다. 번역기 앱(`TulliusTranslator`)이 켜져 있으면 쓰기 명령은 거부한다(GUI와 동시 쓰기 방지).
- 번역 설정(묶음 크기, 용어집·TM·게임 사전 사용 여부 등)은 GUI에 저장된 설정을 읽어 쓰고, 녹화·재생에 필요한 값만 위의 고정값으로 덮는다.

### 요청·결과 파일

- 요청 파일(`request-0001.json`)
  - 프로젝트, 행 ID 목록, 프롬프트 해시, 모델 프로필, 프롬프트 전문(`prompt`), 응답 형식 설명, 글자 수
- 결과 파일(`response-0001.txt`)
  - 모델이 프롬프트가 요구한 그대로 쓴 응답(지금 API 응답과 같은 JSON)

모델은 프롬프트를 읽고 결과 파일만 쓰면 된다. `submit`이 해석 오류를 내면 무엇이 틀렸는지(JSON 형식, 빠진 ID, 깨진 토큰) 알려 주고, 모델은 같은 요청에 결과를 다시 쓴다.

## 안내 파일

- `AGENTS.md`(본문)
  - Codex가 읽는다.
  - 안티그라비티가 읽는 파일 이름은 구현 때 확인한다.
- `CLAUDE.md`, `GEMINI.md`
  - `AGENTS.md`를 가리키는 한 줄만 둔다. Claude Code는 `CLAUDE.md` 안의 `@AGENTS.md`로 그 파일을 불러온다.

`AGENTS.md`에 적을 것:

1. **역할**: 이 폴더는 스카이림 모드 번역 도구다. 번역 요청을 받으면 아래 절차대로 `tullius.exe`를 쓴다.
2. **절차**: open → context → next/번역/submit 반복 → check/edit → export → 보고
3. **금지**
   - DB·플러그인 파일을 직접 고치지 않는다.
   - 외부 AI API를 부르지 않는다.
   - 용어집을 묻지 않고 바꾸지 않는다.
   - 프롬프트의 응답 형식을 바꾸지 않는다.
4. **번역 규칙 요약**: 자세한 내용은 프롬프트에 있다.
   - 내장 TM은 유저 번역이다.
   - 이름은 `lookup` 결과를 따른다.
   - 화자별 말투를 한 가지로 유지한다.
5. **사용량**: 한 번에 몇 묶음을 하고 진행을 알릴지, 한도에 걸렸을 때 `status`로 이어서 하는 방법
6. **보고 형식**: 번역한 줄 수, 품질검사 결과, 남은 일

## 배포

릴리스에 "에이전트 키트" zip을 따로 낸다.

```
TulliusAgentKit/
  tullius.exe        (CLI 단일 실행 파일, Core 공유)
  AGENTS.md  CLAUDE.md  GEMINI.md
  docs/agent/        (절차·규칙 상세, 문제 해결)
  사용법.txt          (앱별 폴더 여는 법, 첫 요청 예시)
```

- GUI 번역기와 같은 버전 번호로 함께 낸다. 같은 Core를 쓰므로 품질 규칙이 어긋나지 않는다.
- 사용자 안내: "구독 앱에서 이 폴더를 열고 '○○.esp 번역해 줘'라고 말하세요."

## 구현에 필요한 정리

- **GUI 프로젝트에 있는 코드**
  - CLI가 GUI와 같은 결과를 내려면 다음을 그대로 써야 한다. 모두 화면(WPF)에 의존하지 않는 서비스다.
    - 실행 연결: `TranslationRunnerService`
    - 게임 사전: `GameStringService`
    - 경로: `ProjectPaths`
    - 내장 용어집·TM 시드와 이관: `BuiltInGlossaryService`, `BundledFranchiseTmSeedService`, `GlobalProjectDbService`
    - 저장된 설정: `AppSettingsStore`
  - 시험판에서는 CLI 프로젝트가 App 어셈블리를 참조해 바로 쓴다. 키트를 배포할 때는 이것들을 새 공용 라이브러리로 옮긴다. CLI가 WPF 앱 전체를 끌고 다니지 않게 하기 위해서다.
- **파이프라인 옵션**: `TranslateIdsRequest`에 녹화·재생용 설정 묶음을 둔다.
  - 동시성 1, 재시도 1
  - 프롬프트 캐시·후보 재순위·품질 상향·세션 용어 기억 끔
  - 고정 모델 프로필
- **새 테스트**: 지금 `PluginDialogueScopeTests`의 가짜 클라이언트 방식으로 만든다.
  - 녹화한 첫 요청의 프롬프트가 같은 줄을 가짜 API로 번역할 때의 첫 프롬프트와 같은지(남은 줄 전체 범위, 대화 맥락 포함)
  - 재생으로 저장된 줄이 같은 응답을 준 가짜 API 번역과 같은지
  - 녹화 뒤 "번역 중"으로 남은 줄이 없는지, 분할 재시도가 일어나지 않는지
  - 토큰 세기 호출이 녹화되지 않는지
  - 프롬프트 해시가 다르면 아무것도 저장하지 않는지, 대기 중인 요청이 있으면 `next`가 거부하는지
  - 토큰이 깨진 응답이 같은 줄의 재요청으로 녹화되는지

## 위험과 대응

| 위험 | 대응 |
|---|---|
| 구독 사용량 한도(5시간·주간)로 큰 모드가 중간에 멈춤 | 모든 상태를 DB·작업 폴더에 남기고 `status`로 이어 하기. 안내 파일에 묶음 수 조절법 |
| 묶음마다 긴 프롬프트가 들어가 사용량을 많이 씀 | 1단계는 프롬프트 전문으로 측정. 많으면 공통 규칙을 처음 한 번만 보내는 짧은 형식을 2단계에 검토 |
| 모델이 절차를 벗어남(파일 직접 수정 등) | 쓰기는 CLI만, 앱 실행 중 거부, `submit` 검증에서 형식 오류는 저장하지 않음 |
| 앱 샌드박스가 연 폴더 밖 쓰기를 막음(Codex는 기본으로 막고, Claude Code는 매번 허락을 물음) | 작업 파일은 키트 폴더 안. 프로젝트 DB 위치는 시험판에서 앱별로 확인하고, 막히면 키트 안 `projects\` |
| 묶음 사이 이름 표기 흔들림(실행 안 이름 기억이 `submit`마다 새로 시작) | 품질검사 이름 일관성으로 확인, 필요하면 기억을 작업 폴더에 보존 |
| 모델마다 품질 차이 | 같은 프롬프트·후처리·품질검사. 앱별 시험 결과를 문서에 기록 |
| 각 회사 약관·요금제 변경 | 원칙 1·2(도구는 AI 호출 없음, 앱을 몰래 실행하지 않음)를 지키고, 배포 전 앱별 조건 재확인 |

## 시험판 구현 (2026-10-18)

- **코드**

  - `context`와 `lookup`은 아직 없다.
  - 시험용으로 `--projects`(프로젝트 DB 위치)와 `--work`(작업 폴더)를 받는다.
- **구현하며 바뀐 것**
  - **새 실행으로 다시 녹화**: 한 실행 안에서 답을 쓴 뒤 만난 다음 요청은 방금 답한 줄이 아직 그 실행의 줄이던 때 만들어진 것이다. 다음 실행에서는 프롬프트가 달라진다. 그래서 답을 쓴 실행이 다음 요청에서 멈추면, 새 실행을 한 번 더 돌려 그 첫 요청을 대기 요청으로 둔다. 모델 호출이 없는 로컬 실행이라 비용은 들지 않는다.
  - **글 요청**: 묶음에 한 줄만 남으면 파이프라인은 JSON이 아닌 글 요청(`<<<TEXT … TEXT>>>`, 끝 토큰 `__XT_PH_9999__`)을 보낸다. `request.md`가 형식마다 답하는 법을 따로 안내한다.
  - **묶음 크기**: 기본 30(GUI 기본은 12). 요청마다 들어가는 지시(약 6~9천 자)를 줄이려고 늘렸다. 프로젝트를 열 때 정해지고(`--batch-size`), 녹화·재생에서 바뀌지 않는다.
